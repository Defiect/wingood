# Safe `--all` research

## Finding

The COM API can discover ordinary applicable updates and respects WinGet user pins, but it cannot tell this helper which installed packages WinGet CLI will skip from `upgrade --all` because their recorded `PinnedState` is `PinnedByManifest` (`RequireExplicitUpgrade`). The CLI applies that exclusion as a separate bulk-operation filter after version selection. This confirms the helper's existing limitation in [winget-api-notes.md](winget-api-notes.md).

WinGet CLI source was checked at commit [`3d9083c062c1e7a7086e05becb414d4e005e4ab6`](https://github.com/microsoft/winget-cli/commit/3d9083c062c1e7a7086e05becb414d4e005e4ab6).

The source distinction also appears in a read-only run on this PC: `winget upgrade --source winget --disable-interactivity` printed 36 main-table rows, then named `MSYS2.MSYS2` in a separate explicit-upgrade table; the reported total was 37 and three unknown-version packages were skipped. The main table excludes MSYS2; the total count includes it. Reading every package ID anywhere in the output would incorrectly include it.

## What each interface exposes

- **COM:** `CatalogPackage.IsUpdateAvailable` and `DefaultInstallVersion` report the latest applicable version. The applicability selector uses `PinBehavior::ConsiderPins`, so version pins are respected. The public `PackageVersionMetadataField` enum contains installer type, scope, location, and uninstall fields, but no `PinnedState`; `CatalogPackage.IsUpdateAvailable` does not apply the CLI bulk-only `PinnedByManifest` filter. See [`PackageManager.idl`](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/PackageManager.idl#L348-L397), [`CatalogPackage.cpp`](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/CatalogPackage.cpp#L56-L128), and [`PackageVersionSelection.cpp`](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerRepositoryCore/PackageVersionSelection.cpp#L159-L205).
- **CLI bulk flow:** `UpdateAllApplicable` checks installed metadata `PinnedState == PinnedByManifest` and skips those packages. The comment says this is unconditional, even if the selected update's manifest does not require explicit upgrade, so this is the behavior to preserve. `--include-pinned` changes version-pin behavior; it does not remove that manifest-pin skip. See [`UpdateFlow.cpp`](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Workflows/UpdateFlow.cpp#L60-L90) and [`UpdateFlow.cpp` bulk filter](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Workflows/UpdateFlow.cpp#L212-L281).
- **CLI output:** `winget upgrade` with no package and no `--all` is list-only; adding `--all` prints the table and then performs upgrades. Although printing occurs before `UpdateAllApplicable`, the printing workflow independently splits normal candidates and explicit-only candidates into separate tables using the same installed `PinnedState` check. The first table can therefore supply the missing exclusion when intersected with COM applicability results. It is human-readable text, so extracting it requires a parser with output-format checks. `UpgradeCommand::GetArguments` has no JSON/dry-run candidate output. See [`WorkflowBase.cpp` table separation](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Workflows/WorkflowBase.cpp#L1244-L1284), [`UpgradeCommand.cpp`](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Commands/UpgradeCommand.cpp#L40-L90), and its [execution order](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Commands/UpgradeCommand.cpp#L155-L190).
- **PowerShell module:** `Get-WinGetPackage` returns PowerShell wrapper objects over the same COM `CatalogPackage`; its exposed `IsUpdateAvailable`, ID, installed version, and version properties do not add the missing manifest-pin state. Converting them to JSON only serializes the same incomplete data. `Export-WinGetPackage` is for downloading a specified package, not exporting an upgrade candidate set. See [`PSCatalogPackage.cs`](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/PowerShell/Microsoft.WinGet.Client.Engine/PSObjects/PSCatalogPackage.cs#L15-L120) and [`Export-WinGetPackage` help](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/PowerShell/Help/Microsoft.WinGet.Client/Export-WinGetPackage.md).
- **`winget export`:** This writes an installed-package configuration/import file; it does not report the CLI's upgrade-all eligibility decision. It therefore cannot serve as the missing allowlist. See [ExportCommand.cpp](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Commands/ExportCommand.cpp).

WinGet stores the manifest-pin state in its per-source `installed.db` tracking catalog: `RecordInstall` writes `PinnedState = PinnedByManifest` when the installed manifest has `RequireExplicitUpgrade`. The DB path is under WinGet's `LocalState`, partitioned by a source-derived path component. Although a private adapter could read this metadata and join it to COM candidates by installed package identity, this is not a supported API. WinGet opens and repairs this database through its own SQLite index and a private cross-process lock; reading it directly introduces schema, path, locking, stale-data, and identity-matching risks. It is a poor foundation for safe bulk installs. See [`PackageTrackingCatalog.cpp`](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerRepositoryCore/PackageTrackingCatalog.cpp#L19-L70) and [tracking metadata writes](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerRepositoryCore/PackageTrackingCatalog.cpp#L237-L288).

## Recommendation

For this project's goal of hands-off bulk upgrades with concurrent downloads, use the CLI's read-only first upgrade table as an allowlist, intersect it with COM candidates, then submit the resulting selection through the existing helper. Use consistent source/scope filters, validate complete package IDs, exclude later explicit-only/pinned tables, preserve unknown-version and pin checks through COM, and reject unrecognized or ambiguous output instead of guessing. Provide `--all --dry-run` to inspect the resulting automatic plan without upgrading. This is a practical approach for the local tool, with the maintenance cost of parsing human-readable output. It does not establish full equivalence with every native bulk-flow behavior.

Delegating execution to `winget upgrade --all` preserves the native bulk flow but also restores the serial download/install behavior the project is intended to improve. It is therefore a fallback, not the recommended implementation. A long-term alternative is an upstream COM addition exposing the installed explicit-upgrade marker or bulk eligibility as structured data. Directly reading `installed.db` also remains possible but depends on private storage details. Do not silently feed every `IsUpdateAvailable` candidate to COM `UpgradePackageAsync` under the name `--all`.
