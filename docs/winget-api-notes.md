# WinGet COM API notes for the updater

These notes use the Microsoft `winget-cli` source snapshot at commit [`3d9083c`](https://github.com/microsoft/winget-cli/commit/3d9083c062c1e7a7086e05becb414d4e005e4ab6), plus the project targeting .NET 10 and `Microsoft.WindowsPackageManager.ComInterop` 1.30.100-preview. The scaffold's `new PackageManager()` discovery and an elevated three-package upgrade batch have succeeded against the installed out-of-process WinGet server (1.30.110-preview).

## Activation and operation shape

`Microsoft.WindowsPackageManager.ComInterop` supplies the WinRT projection. WinGet's own PowerShell client activates the installed COM class (and uses a manual activation path when elevated); the COM API design describes the server as out of process. Keep the current projection and factory linkage in the project. Avoid depending on a private CLSID or loading WinGet's implementation in process. [ComInterop NuGet package](https://www.nuget.org/packages/Microsoft.WindowsPackageManager.ComInterop/1.30.100-preview), [WinGet PowerShell activation factory](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/PowerShell/Microsoft.WinGet.Client.Engine/Helpers/ManagementDeploymentFactory.cs#L104-L205), [COM API design](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/doc/specs/%23888%20-%20Com%20Api.md#L194-L219).

An elevated activation failure with `0x800706BA` was traced to the packaged COM transport, not to a required application-side factory replacement. Inspection of the shipped x64 static `Microsoft.Management.Deployment.dll` in [`ComInterop` 1.29.380](https://www.nuget.org/packages/Microsoft.WindowsPackageManager.ComInterop/1.29.380) found `ncalrpc`; the [`1.30.100-preview` package](https://www.nuget.org/packages/Microsoft.WindowsPackageManager.ComInterop/1.30.100-preview) uses `ncacn_np` and the `\pipe\WinGetServerManualActivation_` endpoint. The tagged `WinGetServerManualActivation_Client.cpp` source still shows the named-pipe transport for both versions, so the NuGet binaries are the evidence for the shipped transport difference. This matches the [reported elevated failure and maintainer diagnosis](https://github.com/microsoft/winget-cli/issues/6560). On this host, `1.30.100-preview` successfully activated against installed WinGet `1.30.110-preview`; this verifies that specific version pairing, not general cross-version compatibility.

The public API offers one asynchronous `UpgradePackageAsync(CatalogPackage, InstallOptions)` call per package; it does not expose a batch-upgrade method. Submit each selected call without awaiting it immediately, retain each operation, attach its progress handler, and await/collect all results. The server queues these requests: up to three download workers feed one install-operation worker. Duplicate requests for the same package and source are rejected while one is queued or running. Submitting several requests also does not promise install order; downloads can finish in a different order, so treat completion/install order as unspecified. [API declaration](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/PackageManager.idl#L1670-L1705), [operation enqueue](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/PackageManager.cpp#L953-L1005), [queue limits and duplicate guard](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/ContextOrchestrator.cpp#L49-L113).

Use one `PackageManager` instance and one async coordinator in the console app. The module's `PackageManagerWrapper` is internal and not a public concurrency contract; parallel PowerShell runspaces or custom apartment/thread handoffs add COM lifetime and callback complexity without increasing WinGet's own worker limits.

## Package selection and MVP scope

For package discovery, create a composite catalog from registered, non-explicit remote catalogs, use `CompositeSearchBehavior.LocalCatalogs` to find installed packages with their available remote versions, and match supplied IDs with an exact ID filter. Handle source connection failures and ambiguity before queuing an operation. Gate every upgrade on `CatalogPackage.IsUpdateAvailable`, then use `DefaultInstallVersion` as the selected version. `DefaultInstallVersion` can fall back to the first available version when no applicable default exists, so calling `UpgradePackageAsync` alone is not a safe “is upgrade available?” check. [Composite search modes and package properties](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/PackageManager.idl#L600-L670), [default-version fallback](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/CatalogPackage.cpp#L58-L95).

The default applicability calculation compares available versions with the installed version, checks the WinGet pin database using `PinBehavior::ConsiderPins`, and builds installer-selection rules from installed package metadata. This respects user pins and existing installer type/scope/architecture/locale when determining `IsUpdateAvailable`. The COM surface does not offer the CLI's `--include-pinned` behavior; for this MVP, show the API's update-available result and skip packages it rejects rather than bypassing pin rules. [Applicable-version selection](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerRepositoryCore/PackageVersionSelection.cpp#L159-L205), [pin modes](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerRepositoryCore/Public/winget/PinningData.h#L23-L38).

Keep the initial contract to explicit package IDs plus dry-run. Do not describe it as equivalent to `winget upgrade --all`: the CLI bulk flow skips packages marked `PinnedByManifest` for `RequireExplicitUpgrade`, but the COM metadata enum does not expose `PinnedState`, and COM `IsUpdateAvailable` does not apply that CLI bulk-flow filter. This is an inference from the selection and metadata implementations. `InstallOptions` has `AllowUpgradeToUnknownVersion`, but there is no matching bulk-discovery option; the API also does not expose the CLI's `--include-pinned` policy. [Installed tracking records `RequireExplicitUpgrade`](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerRepositoryCore/PackageTrackingCatalog.cpp#L265-L285), [CLI bulk filter](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Workflows/UpdateFlow.cpp#L248-L281), [COM metadata fields](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/PackageManager.idl#L348-L366), [upgrade options](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/PackageManager.idl#L1125-L1158).

## Installer options, dependencies, progress

`InstallOptions` defaults to `PackageInstallMode.Default`, accepts package agreements by default, and installs dependencies by default. A catalog reference also accepts source agreements by default. `Default` may show installer UI. Set `PackageInstallMode.Silent` for unattended updates; surface agreements before relying on the default acceptance, and leave dependencies enabled unless the user chooses otherwise. WinGet's COM install flow downloads package dependencies before the operation stage, then installs dependencies before the selected package. [Option defaults](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/InstallOptions.h#L46-L76), [source-agreement default](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/PackageCatalogReference.h#L42-L55), [COM download/install sequence](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Commands/COMCommand.cpp#L20-L51).

The API reports `Queued`, `Downloading`, `Installing`, `PostInstall`, and `Finished`, plus download bytes/percentage when WinGet can measure them, installer progress when the installer reports it, and result status, HRESULT, installer error code, and reboot requirement. It has no whole-install percentage, CPU, or disk counters. Timestamping each operation's state and byte updates can produce useful timelines, but label them as WinGet-reported phases. Dependency installs happen before the target package reaches `Installing` and are not a separate progress state. The target's `Installing` event is raised before it acquires WinGet's cross-process install mutex, so it does not prove the native installer has started; MSIX and Store installers are exempt from that mutex. Cancellation prevents queued work or interrupts downloads; during `Installing`/`PostInstall`, it does not stop the installer or roll back cleanup. [Progress/result contract](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/PackageManager.idl#L10-L62), [progress mapping](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/Microsoft.Management.Deployment/PackageManager.cpp#L376-L466), [COM dependency/install sequence](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Commands/COMCommand.cpp#L20-L51), [install event and mutex boundary](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Workflows/InstallFlow.cpp#L290-L303) and [execution workflow](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Workflows/InstallFlow.cpp#L390-L405) and [state transition](https://github.com/microsoft/winget-cli/blob/3d9083c062c1e7a7086e05becb414d4e005e4ab6/src/AppInstallerCLICore/Workflows/InstallFlow.cpp#L590-L605).
